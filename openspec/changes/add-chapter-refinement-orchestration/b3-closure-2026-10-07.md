## 做了什么

重建的是**整个服务对象、仓库与引擎实例**，不是同一个实例继续跑：

1. 第一次生命周期：真实 service 建 run → 跑到停靠点 → 取消 → 落 checkpoint。
2. 模拟进程被杀：用独立的 repository 实例把记录状态强制写回 `running`（作者来不及收尾的真实形态）。
3. 销毁原 service，**新建** repository / service / engine，`onModuleInit()` 触发启动恢复，
   遗留 `running` 必须收敛为 `paused` + `pauseReason=process_restart` + `resumable=true`。
4. 作者 resume 后继续跑完，断言恢复语义。

隔离与清理：每个用例 `refinement_test_<random>` 独立 schema，跑完只 drop 自己的 schema；
需要的表用仓库内 SQL 迁移脚本回放。**没有配置 `REFINEMENT_PG_TEST_URL` 时 6 例全部显式 skip，skip 不算通过。**

假 gateway 用「按模板第 N 次调用挂起」（`hangOnNth(templateKey, nth)`）控制时机，
而不是等固定秒数：诊断停靠点用长章 + `diagnosisTargetChars: 2000` 造出多个诊断窗，
inspect 脚本按 prompt 里实际出现的 `<block id="...">` 生成，避免脚本与规划脱节。

## 红灯与绿灯

**绿灯（恢复实现 + 真实 PG）**

```

node --import tsx --test src/modules/projects/chapter-refinement.pg-rebuild.test.ts

```

**红灯（反证：把 `rebuild()` 改成"不销毁、不新建，直接复用旧 service"）→ 5 fail / 1 pass**

失败原因（摘）：

- `pauseReason` expected `process_restart` / actual `user_cancelled`（旧实例没有真正重启）
- `gateway.calls` expected `0` / actual `5`、`10`（旧实例残留调用，"未继续前零调用"被蒙混）
- E1 用例 expected `boundary_conflict` / actual `user_cancelled`

唯一仍通过的是「原文版本变化 → 1307」——该分支在重建语义之前就被拒绝，属预期。
**这说明四个停靠点与"未继续前零调用"确实依赖新进程重建，不是复用实例就能过的软断言。**
