## 3. B1：把应用门禁和问题生命周期一次修完整

### 实施原则

1. 移除依靠历史 `retained_original` 提示集合推断“其他 unresolved 可豁免”的行为。缺失 unitId 不能用于匹配；相同 unitId 也不能证明不同版本、不同问题已消除。
2. 候选仍生效的 high/medium 阻断若 unresolved，终态必须 paused，UI 应用不可用。全章/跨范围/无法定位的阻断按同样规则处理。
3. 对确实因修复/回退而消除的问题，在完成实际候选及接缝复检后，显式更新问题 disposition 与处置说明。记录关联的范围、候选版本和处理依据。
4. 回退提示本身继续展示为 retained_original；被消除的旧候选问题单独结案。复检失败、未完成或有新阻断时保持暂停。
5. 抽取清楚的完成判定函数，覆盖检查完成、覆盖完整、存储确认、问题处置。重用在正常完成与恢复后的完成路径；保留旧优化入口行为。
6. 中途 checkpoint 保存正文、替换、问题结论和检查记录的一致快照。旧 checkpoint 缺少必要关联信息时保守复检或暂停，不默认判已解决。

### 必须先写的红灯

- 原 E1：两场，另一场超长保留且无 unitId，全章阻断暂停后继续，必须仍暂停。
- 有有效 unitId 的回退：回退确实消除本范围旧问题，接缝复检完成后允许 ready_with_issues。
- 同一 unitId 的旧版本保留提示不能豁免新版本阻断。
- 其他单位/其他场的保留提示不能豁免当前问题。
- 全章/跨范围问题，没有 unitId 或唯一锚点时不可应用。
- 复检确认误报/已解决，账本显式结案；不能一直保留 unresolved 却开放应用。
- repair/revert 后取消、继续、存储失败：正文、变更清单、问题和应用资格一致。

重点文件：engine、engine/service tests、refinement UI 应用资格测试。完成证据必须含实际 checkpoint 的初次运行及 resume，不只验证一个集合函数。

## 4. B2：给散场证据定义可信边界

### 先同步内部输出合同

实施者先更新 prompt-design.md 的 review 合同及相关类型，明确“引文命中”和“末态成立”的不同证据要求。不要再仅通过新增一个由模型自行命名的字符串字段宣称末态验证完成。

最小证据记录应能表达：

- 所属场景/单位和当前候选 revision/hash。
- 引文在候选中的唯一位置；偏移由程序定位，不直接信任模型数字。
- 状态的确认/最后变化证据，以及是否有后续相关变化。
- 提取不确定、只有历史证据或存在冲突时，不进入确定状态集合。

程序负责检查候选版本、来源范围、唯一位置与已报告变化的顺序。人物行为的语义判断仍需要 review 和模型评测；这些限制必须在完成报告中明确。

### 执行策略

1. 利用现有 review 同时提供证据位置与末态判定，不默认新增每单位一次模型调用。
2. 以范围末尾的状态确认或最后相关变化为依据；证据范围由程序的句段/已验证拍界定位。不能仅从候选任意位置取一段历史动作。
3. 原反例“入场拿着钥匙，散场放在桌上”：入场片段改名为 exitAnchorQuote 后仍必须被拒绝为确定末态；正文后续相关变化必须进入审查。
4. 重复引文、多次转移、末尾对话及跨段持续状态有歧义时，保持未确认并使用实际已接受邻文。不要把所有有效状态强迫改写成末句陈述，也不要靠“入场/散场”等关键词通用判断。
5. 修复、回退或候选版本改变后，使受影响状态证据失效；复检产生新证据后再向下游传递。checkpoint/恢复保存同一版本的事实。
6. 已锁定的必要事实、逐字锁和首尾状态仍按原合同校验；不能借“不确定”删除必要事实或把有值锁改 null 放行。只对新增提取事实采取保守传播。

### 验收矩阵

入场持有/散场放下、入场引文冒充末态、重复引文、同物件多次转移、原文/候选相反、修复/回退改变末态、持续状态后面是无关对话、旧候选 hash、取消/恢复、必要事实不能降 null。每例同时验证接受/拒绝结论和下一单位实际收到的输入。

完成标准：已定位的候选证据与语义确认分层；当前 W6 反例不再进入确定状态；不确定结果不污染下游；没有无界重试或新增大段创作。文学语义的普适准确率留给 AQ-386。

## 5. B3：补真正的 PG 服务重建测试

测试使用独立测试 URL 和随机临时 schema，测试结束只清理自身 schema。没有测试数据库时显式 skip；正式验收环境必须实际执行该分支。

使用真实 PG repository + ChapterRefinementService + engine + 可控假 gateway。第一次生命周期写 checkpoint 后终止并销毁实例，第二次创建新的 repository/service/engine，执行启动恢复，再由作者 resume。不能用同一个 service 或 Map 仓库替代重建。

至少四个停靠点：

| 停靠点 | 重建后断言 |
|---|---|
| inspect 完成部分窗口 | 已完成诊断不重复；成果和当前位置保留 |
| 已接受一单位，下一单位在途 | 接受稿保留，临时稿舍弃；新 attempt 不被旧回调覆盖 |
| 单位 repair 已开始 | repair 名额与历史调用数保留；同单位不会重新获得补修次数 |
| 最终接缝 repair/recheck 在途 | seam 名额、候选版本、问题账本保留；继续后检查完成才能应用 |

统一断言：重启状态 paused/process_restart；作者未继续前 gateway 调用为零；模板/模型/参考材料仍冻结；历史用量不归零，新尝试预算按既有合同计算；权限/原文版本改变拒绝继续；E1 在 PG 恢复下仍不可应用。

## 6. B4：假模型浏览器完整作者路径

优先采用真实 Web + 真实 API/service/engine + 脚本 gateway + 隔离测试项目。测试用用户只在测试环境创建，无真实模型请求、无真实作者章节和密钥。

网络 mock 可以用于额外 UI 故障测试，但至少一条主闭环走真实 API、SSE 与 apply。浏览器模拟 API 所有响应不能代替这一集成证明。

必须覆盖：

1. 启动 → 看到进度 → 关闭重开/刷新 → 同 run 恢复，临时稿不冒充接受稿。
2. 取消 → 保留接受稿 → 继续 → 同 run、新 attempt，旧调用不能覆写。
3. 完成后重新开始，新 clientRequestId；创建请求的网络重试复用原 key。
4. 检查未完成/E1 阻断/保存失败，按钮不可应用。
5. 原文版本变化，resume/apply 走 1307，不覆盖新正文。
6. 正常 ready/ready_with_issues → 明确确认 → 真实 apply 成功，UI 和持久化正文等于返回结果，摘要策略正确。
7. 旧方案改写、直接改写、自动循环、按场成稿及未保存章节保护继续通过。

控制时机使用阶段屏障/等待条件，不用固定等待若干秒代替状态断言。每例记录 runId、attemptId、源/候选 hash、最终状态及截图或 trace；不输出私有正文或凭据。

## 8. B5：Prompt 入口与阶段隔离

### Settings 编辑入口

在现有 Settings 显示五个 `chapter.refinement.*` 模板，标明诊断/规划/正文/检查/补修职责和 utility/writing 档位。复用现有草稿、发布、回滚能力，不新增编辑系统。

作者能修改项目文风指导、五个任务模板和本次章节要求。运行中的模板文本/版本/hash 仍冻结，修改发布只影响新 run。运行中不增加任意替换内部 Prompt 的能力。

测试：五模板都可见；草稿不影响正式运行；发布影响新 run；回滚生效；修改期间旧 run/恢复继续使用旧文本；旧任务分组仍在。

### 阶段注入矩阵

| 阶段 | 项目长写作指导 | 文风样本 | 阶段目标与必要事实 |
|---|---|---|---|
| inspect | 不注入 | 不注入 | 当前窗、范围/策略、相关要求 |
| plan | 不注入 | 不注入 | 简明编辑目标、诊断汇总和必要事实 |
| rewrite | 冻结版本 | 冻结适用样本 | 场内交底、首尾、锁、真实邻文 |
| review | 不注入 | 不注入 | 明确检查目标、候选、原文和边界 |
| repair | 冻结版本 | 冻结适用样本 | 当前具体缺口、目标候选和边界 |

不能从作者自由文本自动截几句或删除部分内容冒充“简明偏好”。需要用于 utility 的偏好由本次编辑目标/明确合同表达；作者的完整创作指导由 writing 执行。

检查 engine → gateway → orchestrator 最终组装的完整 system/user 消息，防止 omit 标志被 override 重新开启。预算依据该阶段实际发送的全部材料计算。用标记文本捕获假 provider 的最终消息，断言 writing 出现指导/样本、utility 不出现，同时事实和任务合同仍在；不只断言请求 body 字段。

更新模板时同步治理包、API、orchestrator 镜像及版本测试，保留灰度/回滚。没有真实模型验收证据时保持草稿/受控入口。
