# B1 收口：应用资格与问题生命周期（AQ-383）

- 日期：2026-10-07
- 分支：`feat/aq-380-refinement-orchestration`
- 依据：[收口执行计划](acceptance-closure-plan-2026-10-07.md) 第 3 节；第四轮验证的 [E1 缺陷](fourth-verification-2026-10-07.md)
- 结论：**E1 已关闭**。无 unitId 的全章保留提示不再豁免无 unitId 的全章阻断；问题结案改为显式处置 + 候选版本匹配；终态判定抽出单一函数供正常完成与续跑共用；UI 应用资格与阻断账本同口径。B2～B5 未开始。

## 修复内容

### 1. 移除「靠历史 retained_original 提示集合推断豁免」

旧守卫先收集 `retained_original` 问题的 unitId 集合，再排除同 unitId 的 unresolved 阻断。全章 / 跨范围记录没有 unitId，集合中会出现 `undefined`，于是另一条同样没有 unitId 的全章高危阻断被误判为「该范围已回退」。

现在不再有任何推断豁免：`disposition=unresolved` 且 severity 为 high/medium 的问题一律阻止进入可应用终态。

### 2. 显式结案（替代推断）

新增 `unitCandidateRevisions`（每单位当前候选版本号）+ `closeSupersededIssues()`：候选每次实际变化（接受改写 / 接受补修 / 接受接缝修复 / 回退原文）递增，问题登记时写入 `candidateRevision`。只有同时满足「同一 unitId + 该问题登记了候选版本 + 该版本严格早于被取代的版本」才显式结案，并把处置依据写进 `message`（`…（候选版本 N 已失效：<原因>）`）。

三类结案点：

| 触发 | 条件 | 依据 |
|---|---|---|
| 单位补修后回退原文 | 同单位、旧版本 | `第 N 段已回退原文` |
| 整章最终接缝回退范围 | 同单位、旧版本 | `范围 <unitId> 已回退原文` |
| 整章最终接缝补修稿通过复检并被接受 | 同单位、旧版本 | `补修稿已通过复检并取代旧候选`（复检是对该范围原文 + 新候选的完整复核） |

缺失 unitId、缺失候选版本、或版本不早于被取代版本，一律不结案——保持 unresolved 并拦住应用。

### 3. 终态判定抽出单一函数

`evaluateTerminalEligibility()` 覆盖三项：整章最终检查已完成、覆盖完整性已校验、无未解决的高/中危阻断。正常完成路径与续跑完成路径（含 `units.length === 0` 的早退路径）共用同一口径。

覆盖完整性改为在**回退索引清空前**校验并存 `finalCheckCoverageVerified`——清空后无法再区分「已回退」与「仍生效」范围，旧代码在清空后重算会把已回退范围再次计入未覆盖。

### 4. 续跑时的保守处理

- 候选版本从已恢复的问题账本反推（取每单位已登记的最大 `candidateRevision`），续跑中的回退 / 补修结案才能正确判定旧版本被取代。
- 旧 checkpoint 声称 `finalCheckCompleted=true` 但覆盖记录缺少仍生效范围时，强制 `finalCheckCompleted=false` 重跑最终检查，不默认认为检查已完成。
- 旧 checkpoint 缺少候选版本信息的问题不结案（无法证明同源）——保守拦住应用。

### 5. UI 应用资格同口径（apps/web）

`resolveRefinementApplyGate` 增加：账本中仍有 `disposition=unresolved` 且 severity 为 high/medium 的问题时不可应用。用于历史 / 既有运行视图的兜底，与引擎终态判定一致。已结案的 retained_original、低危提示不阻断应用。
