## 设计

直接改写第 N 段时，使用第 N-1 段实际生成的正文承接叙述。正文不超过 20000 字符时完整传入，超出时传入末尾 20000 字符并明确标记截取。第 1 段从本段原文和边界锚点起笔。情节事实与前段成稿冲突时遵循下文的情节梳理规则。

采用独立的 `previousSegmentDraft` 字段，避免改变方案改写目前使用 `previousSegmentTail` 的行为。超过上限后的跨段早期状态仍可能丢失，后续根据作者长章试用再决定是否引入累计状态摘要。

## AQ-392 输出额度试验

AQ-393 的后续编辑边界见文末；输出额度策略保持本节原约定。

真实试用出现单段从开头直接跳到后续场景的情况。最近一组五段供应商 trace 均为 `finish_reason=stop`，没有长度截断证据；作者仍选择先把直接改写分段请求提高到项目当前代码的最大输出额度 65536 token 做对照试验。

仅对 `rewriteMode=direct` 且分段生成的每段请求使用该上限；方案改写、整章单段和其他生成路径维持现有额度。编排服务对开启思考的请求额外预留 8192 token，但最终仍按 65536 封顶。这项试验单独验证输出额度对漏写的影响。情节梳理的重试与展示见下文。

## AQ-393 全文表达重写与情节保留边界

作者确认保留充分的全文表达改写，避免只改开头、后半照搬或机械替词；必要短句和自然对白允许保留，不按改动率硬造变化。

删除、合并或重排情节须用户明确授权。默认保留事件、人物互动、连续动作、情绪发展和场景过渡；结果相同、转场流畅不构成用概括句替代中间过程的理由。去冗余仅限重复措辞与解释。明确动作错误可依据上下文调整局部步骤、指代与必要衔接，保留事件目的、人物选择和结果。

直接改写 API 默认、编排兜底与模板包登记同步为 v1.1.3 试用文案；整章/分段追加指令采用相同边界，系统模板同时识别两类原文及前段标记。方案改写分支保持原样。

项目已发布任务全文优先于默认，因此当前项目仅替换相关编辑条款，保留其他自定义内容，并通过原有草稿/发布/版本机制保存回滚点。不得只改仓库默认后声称运行态已生效。

本轮是作者授权的条款对照试用，不宣称已证明模型压缩的唯一原因。用户明确跳过所有测试、构建、自动评测及模型调用；保留 `DOING`，待作者自行验收。

## 分段润色前的情节梳理

### Context

`optimizeChapterDraftStream` 确定本轮改写源文本并调用 `splitIntoSegments`，随后按顺序流式生成正文。`buildSegmentPrompt` 拼装本段原文、相邻边界锚点和上一段成稿。已保存的章节摘要用于检索上下文，时效与本轮输入取决于各自的生成时点。本轮需要一份基于实际输入、能定位到具体分段的情节描述。

### Decisions

1. **先固定切分，再梳理原文。** API 沿用现有改写源文本和切分规则，固定本轮有序分段。仅在 `rewriteMode=direct` 且实际切出至少两段时，调用一次工具档模型，输入按实际段号标记的整章原文。以现有 `Segment.index` 映射到从 1 开始的外部段号，避免预估段数和实际段数不同时发生错配。模型根据原文抽取事实，章节概述交代起因、转折和结果，各段清单按原文顺序描述要保留的事件、动作及人物状态变化。
2. **验证结构后开始润色。** 结构化结果包含非空 `chapterSynopsis` 和 `segments`。每项包含 `segmentIndex` 和非空 `plotChecklist` 字符串数组。解析后按实际段号校验完整覆盖，拒绝重复、越界及缺失段号和空白条目，再按段号取用。输入需覆盖整章原文，预算不足时返回情节梳理失败。结果随本轮请求保存在内存，后续段复用同一份概述，各段只取自己的清单。用户重新点击改写时，以新一轮源文本重新梳理。
3. **分清情节事实与文字衔接。** `buildSegmentPrompt` 在分段直接改写中增加「整章情节」与「本段情节保留清单」两个区块，并继续提供本段原文、边界锚点和上一段成稿。清单帮助模型逐项照应原文中的过程。清单有遗漏或错写时以原文为准。润色遵循原文的人物状态、动作顺序和信息揭晓时机，作者明确要求的情节调整适用既有权限约束。整章概述提示铺垫与后续因果，当前段只呈现其边界内的内容。前段成稿为语气、视角、节奏和叙述承接提供参考。模型在现有正文调用内自查并修正当前段，输出仍为本段正文。事后通过成稿对比发现偏差时，由作者发起重试。
4. **沿用原流式入口和终态。** 在第一个 `draft_segment`、`segment_start` 或正文事件之前发出 `stage=preparing_plot_context`。前端现有进度区显示「正在梳理本章情节」，成功后自动进入分段润色。超时、模型调用失败或结构无效时自动重试一次，连续失败使用成功建立 SSE 后的既有 `error.data` 字符串，内容提示「情节梳理失败」并恢复可重试状态。该失败发生在正文生成前，流以错误结束。用户中断时沿用现有 SSE 生命周期，传递取消信号，停止梳理且不触发重试或正文调用。
5. **先更新合同与模板约定。** 实现时先在 `openapi/paths/projects/chapter-optimize-draft.yaml` 定义新增阶段及适用条件，再同步 API 与 Web 的阶段类型和进度显示。沿用现有请求字段、SSE 事件形状和错误码。梳理任务使用现有工具档模型路由、超时和模板治理机制，正文仍走直接改写的写作档。同步梳理模板及运行时副本，梳理阶段在日志中关联现有 `traceId`，记录阶段、段数、耗时、重试和结果状态。

### Risks / Trade-offs

- 梳理增加首段等待与输入 token 消耗，首次成功只调用一次，并通过显式进度反馈等待。输入超过模型预算时终止并给出原因，整章原文覆盖是分析成立的前提。
- 结构有效的概述仍可能漏掉事实或写入推断。润色时用原文校准清单，并按原文保留关键过程及揭晓时机。验收用含跨段伏笔、中段连续动作和人物状态变化的非敏感样章，对照旧流程记录漏写、错写和提前揭晓的差异。
- 自动化验证覆盖实际段数、顺序与每段上下文、首次失败后恢复、重试耗尽、取消及模式边界。新增提示词按现有模板治理、GS-G 和 GS-C 评测口径验收。
