## Why

直接改写分段时，后一段只收到上一段成稿末尾约 1200 字，可能丢失上一段较早处已改变的人物状态和事件信息，导致沿用旧原文状态。

## What Changes

- 直接改写的后续分段接收紧邻上一段的已生成正文；常规长度下传入完整正文。
- 对异常长的上一段设置输入上限，避免挤占当前段的上下文。
- 作者希望先试提高直接改写分段的输出额度：每段请求使用项目现有的 65536 token 上限。
- AQ-393：保留全文表达重写的目标，区分表达改写与情节删减；未明确授权时保留事件、互动和中间过程，明确动作错误仅做最小修正。
- 同步直接改写默认模板、整章/分段追加指令及当前项目已发布的对应任务全文；保留旧版回滚点。
- 方案改写的现有分段衔接方式保持原样。

## Scope

仅修改服务端分段 prompt 与直接改写分段的输出额度，不变更 API 或 SSE 合同。设计细节见 `design.md`。

AQ-393 将范围补充为直接改写的整章/分段表达边界与任务模板同步，不改变模型、温度、分段、输出额度、方案改写或新增语义审核/自动重试。用户明确要求不运行自动验证及模型调用，质量效果由作者试用确认。
