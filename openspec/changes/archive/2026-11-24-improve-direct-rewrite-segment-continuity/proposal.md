## Why

最初的分段衔接只提供上一段成稿末尾约 1200 字，容易遗漏更早发生的人物状态变化和事件。AQ-391 扩充了上一段成稿的输入。当前分段改写仍主要依赖本段原文、相邻原文锚点和上一段成稿，模型难以判断本段在整章中的作用，也容易漏掉后文依赖的动作或提前揭示后续信息。

## What Changes

- 直接改写的后续分段接收紧邻上一段的已生成正文；常规长度下传入完整正文。
- 对异常长的上一段设置输入上限，避免挤占当前段的上下文。
- 作者希望先试提高直接改写分段的输出额度：每段请求使用项目现有的 65536 token 上限。
- AQ-393：保留全文表达重写的目标，区分表达改写与情节删减；未明确授权时保留事件、互动和中间过程，明确动作错误仅做最小修正。
- 同步直接改写默认模板、整章/分段追加指令及当前项目已发布的对应任务全文；保留旧版回滚点。
- 方案改写的现有分段衔接方式保持原样。
- 当直接改写实际切出多个分段时，按既定边界编号，在开始写作前一次调用模型分析整章原文。分析返回整章情节概述及每段的情节保留清单，记录关键事件、事实与信息揭晓时机。
- 每段的改写输入增加整章概述和当前段清单，继续使用本段原文、相邻原文锚点和上一段成稿。模型在同一次正文调用中对照清单自检，再输出当前段正文。
- 情节分析失败时重试一次。仍失败则通过现有 SSE 错误事件结束本轮，提示用户重新发起，正文生成停在第一段之前。界面只显示分析进度，分析结果随本轮任务结束释放。

## Scope

AQ-391 与 AQ-392 的范围是服务端分段 prompt 和直接改写分段的输出额度。两项均沿用原 API 与 SSE 合同。

AQ-393 将范围补充为直接改写的整章/分段表达边界与任务模板同步，不改变模型、温度、分段、输出额度、方案改写或新增语义审核/自动重试。用户明确要求不运行自动验证及模型调用，质量效果由作者试用确认。

情节分析扩展在现有正文 SSE 中增加 `preparing_plot_context` 进度阶段。实施时先更新 OpenAPI 和项目接口文档，再实现服务端发出及前端展示。沿用现有请求结构、SSE `error.data` 与 `end`，错误码表保持原样。设计细节见 `design.md`。

## Non-Goals

- 适用范围限于实际切出多个分段的直接改写。整章单段和方案改写沿用各自流程。
- 自检在每段正文生成调用内完成。独立语义复核、成稿后的自动修稿和自动回滚属于另外的功能范围。
- 情节分析只作为本轮改写的临时输入。已存章节摘要、分析结果的持久化和用户编辑均不在本轮范围内。
